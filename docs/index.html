The problem

The problem is the origin, not the file

Modern builds use ES modules. Under file:// the browser treats the page as an opaque origin: modules are blocked by CORS, /assets/... resolves to the root of the drive, and service workers do not exist. The file is fine. The origin is not.

file://

What happens when you double-click a build today:

  • Module scripts blocked by CORS
  • Absolute paths point at the drive root
  • No service worker, no manifest, blank page

http://127.0.0.1

What happens when Fenestra serves the same folder:

  • Modules load, exactly like production
  • SPA routes survive a refresh
  • Same tab, same profile, your browser

How it works

Three steps, none of them yours

Fenestra attaches itself to the double-click and decides what the file needs.

01

You open the file

Double-click it, drag the folder onto the executable, or pass a path on the command line.

02

Fenestra decides

It reads the HTML. Needs an HTTP origin? It starts a server on a stable port. Does not? It opens the file directly.

03

Your browser shows it

A normal tab, in your window, with your profile, your extensions and your address bar.

Compatibility

What works, what does not

If the folder works on any static host, it works here. If it needs a build step or a backend, it does not — and Fenestra says so instead of failing silently.

Case Works? Why
dist/ · build/ · out/ Yes Plain HTML, CSS and JS served from the folder.
SPA routes Yes Extensionless paths fall back to index.html, so refresh works.
index.html (single file) Yes Opened directly by Edge through file://, with no server at all.
/src/main.tsx No Source projects need their own dev server to compile.
API · backend No Fenestra serves files. It does not proxy, run services or touch a database.
pages/index.html with ../ No The root is the file's folder, and .. is confined for safety.

Platforms

One idea, three systems

Same job everywhere: turn a folder into localhost and open it in your browser. The packaging changes because each system has its own rules.

Windows .exe

A single 54 KB executable. No installer, no runtime — .NET Framework 4.8 already ships with Windows.

  • Download Fenestra.exe and run it, or make it the .html handler.
  • Build with build.ps1 using the csc that ships with Windows.
Audit the source →
Linux static

One static binary, no runtime, for amd64 and arm64.

  • chmod +x fenestra-linux-amd64 and run it, or use --install to register the handler.
  • Build with CGO_ENABLED=0 go build . inside linux/.
Audit the source →
macOS build

No notarized app bundle: the CLI installs via Homebrew, the Finder app you build locally.

  • cd macos && ./build.command builds the CLI and Fenestra.app.
  • Go only — no Xcode, no Apple account, no quarantine after a clone.

Windows

The 54 KB .exe above runs as-is. No installer, no runtime.

The binary is not code-signed yet, so Windows SmartScreen will ask for confirmation once. That is expected for an alpha build.

Or build it yourself

# requires only the csc.exe that ships with Windows
git clone https://github.com/benedetleandro/fenestra.git
cd fenestra
powershell -ExecutionPolicy Bypass -File .\build.ps1

Make it the default for .html

One time, three clicks. Windows does not let an app do this alone.

  1. Right-click any index.html and choose Open with → Choose another app.
  2. Select Fenestra.
  3. Check Always use this app and confirm.
Windows allows exactly one handler per extension. The handler is invisible; the window that opens is Edge.

On Linux there is a native build: one static binary, no Wine, no runtime. Download fenestra-linux-amd64 from the release and run it with chmod +x.

On macOS there is no prebuilt binary: Apple notarization costs US$ 99/year. The macos/ folder is a build kit — install Go, run one command.

Usage

# open a build
Fenestra.exe "C:\projects\app\dist\index.html"

# open a folder
Fenestra.exe "C:\projects\app\dist"

# force the server, skip detection
Fenestra.exe --serve "C:\path\index.html"

# choose the browser (edge is the default)
Fenestra.exe --browser chrome
Fenestra.exe --browsers

# register / unregister the .html handler
Fenestra.exe --install
Fenestra.exe --uninstall

Browser

Pick the browser, once

Fenestra opens a normal tab in the browser you choose. The choice is saved and applies to every double-click from now on.

On first run, Fenestra asks which browser to use and saves the answer.

Choose it

# Windows
Fenestra.exe --browser firefox

# Linux / macOS
fenestra --browser firefox

# hand the choice to the OS
fenestra --browser default

See what is installed with --browsers.

Use the system default

With --browser default, the operating system decides. To change what that means:

  • Windows: Settings → Apps → Default apps → choose your browser.
  • macOS: System Settings → Desktop & Dock → Default web browser.
  • Linux: xdg-settings set default-web-browser firefox.desktop

Stored in %LOCALAPPDATA%\Fenestra\browser.txt (Windows), ~/.config/fenestra/browser (Linux) and ~/Library/Application Support/Fenestra/browser (macOS).

macOS

Build it yourself — that is the point

There is no notarized binary. Apple charges US$ 99/year for that, and an unsigned download is blocked by Gatekeeper. So you build it locally, from source you can read.

  1. Install Go
    The official installer is signed by Google, so macOS shows no warning. It is the only thing you install.
  2. Get the source
    git clone, or download the ZIP if you do not have git.
  3. Run the build
    The script builds the CLI and Fenestra.app, then re-signs the app after editing the bundle.
  4. Use it from the Finder
    Drag Fenestra.app to /Applications, right-click an index.html, Open with → Fenestra → Always.

No Xcode, no Apple account, no US$ 99. Tested on a real macOS runner in CI (arm64); on Intel the build is native.

Full macOS instructions →

# 1. install Go from https://go.dev/dl/
# 2. get the source
git clone https://github.com/benedetleandro/fenestra.git
cd fenestra/macos

# 3. build (CLI + Fenestra.app)
./build.command

# 4. run
./fenestra ~/projetos/app/dist/index.html

No git? Download the ZIP, extract, and run bash build.command — the shell reads the script, so Gatekeeper is not involved.

Homebrew — CLI only

brew tap benedetleandro/fenestra
brew trust benedetleandro/fenestra
brew install fenestra

Installs the prebuilt CLI for arm64 and Intel. The Finder app still needs the build above.

Under the hood

Small on purpose

One C# file for Windows, and two small Go ports for Linux and macOS. No dependencies, built by compilers you already have — small enough to audit in an afternoon.

ServerHTTP/1.1 on a TcpListener, bound to 127.0.0.1 only. Only loopback Host headers are accepted.
PathsNormalized and confined to the served root. .. , : and ::$DATA are rejected, and so are symlinks that escape it.
PortsFNV-1a hash of the folder maps to a port that is stored and reused, so localStorage survives.
SPA fallbackExtensionless requests return index.html; missing assets still return 404.
Single instanceA second double-click pings the running server and just opens another tab.
LifetimeExits when the Edge it started closes, or after four idle hours.

Security

Local means local

Loopback only, no telemetry, no accounts, no remote code. It serves the folder you opened and nothing else — but every file under that folder is reachable, including dotfiles.

Do not point Fenestra at a directory that contains secrets. The full threat model is in SECURITY.md in the repository.

The name

A window, not a browser

Fenestra is Latin for window: the opening, not the room. That is the whole idea — Fenestra does not render your site, it opens a window onto it and lets your browser look through.

The word survives in Italian finestra, French fenêtre and Portuguese fenestra (the anatomical one), so it reads as "window" to a Romance speaker and as a proper name to everyone else. It is also a quiet joke: a browser is the frame; this is the opening.

FAQ

Questions people actually ask

Does it work with any static site?

Yes. Any folder with an index.html is served as-is. Each folder gets its own stable port, so two apps can be open at the same time without fighting.

Do I need Node.js or any runtime?

No. Fenestra is a single 54 KB executable built against the .NET Framework that ships with Windows. Nothing to install, nothing to keep updated.

Why does Windows ask me to confirm the .html handler?

Because Windows allows exactly one program per extension and does not let an app claim it silently. That is protection against exactly the kind of software that hijacks file associations.

Does it change my files?

No. It opens them read-only, serves them, and writes nothing to the project. The only state it keeps is a port number per folder, under %LOCALAPPDATA%.

Which browsers does it support?

The system browser is the default. Chrome, Firefox, Brave, Vivaldi, Opera and Chromium are detected automatically — plus Safari on macOS — and --browser edge pins Edge. It opens a normal tab in the browser you already use, so there is no engine to patch and no extra 150 MB.

Is Fenestra a browser?

No. It is a server that opens a tab in your browser. There is no address bar of its own, no tabs, no rendering engine. That is the point.

Will it run on macOS or Linux?

Yes. Linux has static binaries (amd64 and arm64) with a --install flag. macOS has no prebuilt binary: the macos/ kit builds on your machine, with no Apple account and no US$ 99/year notarization.
